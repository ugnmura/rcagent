I looked at the BGL logs for 11 June 2005, 00:00–24:00 UTC (the table's own time zone), all components, and focused on the most severe levels: FATAL, FAILURE, SEVERE and ERROR.

## What failed

One compute node, **R30-M0-N9-C:J16-U01**, had a storm of fatal kernel errors. The kernel belongs to the **Node OS** team.

- **"data TLB error interrupt"** [T1]: **152,182 entries**, all FATAL and all on that one node [Q52]. This is almost every serious entry that day: the day had 152,183 FATAL kernel entries and no FAILURE, SEVERE or ERROR entries at all [Q49].
- **"machine check interrupt (bit=0x10): L2 DCU read error"** [T2]: **1 entry**, on the same node [Q52].

These are entries, not separate incidents. All of them come from one node in one continuous stretch, so they most likely make up a single episode that logged many lines.

When it happened [Q51]:
- It started at **17:17:44 UTC**. The first line was the single machine check error, and the first TLB error followed in the same second [Q53].
- It ran at about 23,000–24,000 entries per hour from 18:00 to 22:00 (for example, 24,321 in the 18:00 hour) [Q51].
- The last TLB error was at **23:39:32 UTC** [Q57]. There were none on 12 June [Q56].

## What happened just before and after

**Before:**
- Nothing at all was logged anywhere on the system in the 30 minutes before 17:17:44 [Q54].
- The last entries before that were routine INFO messages on other nodes:
  - 15:19:29: "ddr: excessive soft failures, consider replacing the card" on R16-M1-N2-C:J17-U01
  - 14:29–14:11: corrected DDR and L3 EDRAM memory errors on R35 nodes
  - around 12:16–12:24: "MidplaneSwitchController performing bit sparing on R27-M1-L3-U18-C bit 3" (link card) [Q55]
- None of these were on the failing node.
- This node had no FATAL entries at all before 11 June [Q59]. Its only earlier entries were 14 INFO lines of **"generating core.1536"** on 5–7 June, the last at 7 June 15:32:14 UTC [Q60].

**After:**
- 23 seconds after the last TLB error, the control system's services were restarted. At 23:39:55–23:39:56 UTC it logged "idoproxydb has been started", "mmcs_db_server has been started … --reconnect-blocks all" and "ciodb has been restarted" [Q58].
- The same three restart messages appeared again at 00:08:00 UTC on 12 June [Q58].
- On **13 June at 04:47:27 UTC**, the same node logged the same "machine check interrupt (bit=0x10): L2 DCU read error" again. This time it came with "instruction address: 0x0035bc24" and "machine check status register: 0xe0800000". The node logged 46 FATAL entries that day [Q61].

## Possible cause (hypothesis, not established)

**Hypothesis:** the processor's L2 data cache on R30-M0-N9-C:J16-U01 has a hardware fault. One cache read error then triggered a kernel loop that kept raising TLB error interrupts until the control system was restarted.

What points to it:
- The storm began in the same second as the L2 cache read error [Q53].
- It stayed on that one node [Q52].
- It ended right before the control-system restart [Q58].
- The same cache error came back on that node about 29 hours later [Q61].

**Alternative hypothesis:** a software fault, for example in the job running on the node. The earlier "generating core" messages on that node [Q60] fit with crashing jobs. Nothing in the logs links them to this failure, though.

## Next check

Look at every entry for **R30-M0-N9-C:J16-U01 from 13 June onwards**, especially whether the L2 cache error keeps coming back (count it per day for the rest of the period), and compare with a hardware swap or repair record for that node card.
- **Error keeps recurring on this node only, and stops after the card is replaced:** that supports a hardware fault.
- **Same cache error and TLB storm also show up on other nodes running the same job:** that points to software instead.

## What the logs do not establish

- Whether jobs failed, how much compute time was lost, or which users were affected. None of this is in the logs.
- Whether the 23:39 control-system restart was a deliberate fix by an operator or happened for some other reason. The logs only show that it happened.
- Why the TLB errors repeated, and whether the node actually stopped working or only kept logging.
- Whether this was the first such storm across the whole system. The analysis tool labelled both error types as new, but that only means it hadn't catalogued them before; it is not a finding about the data. What I can say is that this node had no fatal entries before 11 June [Q59].

# What to prioritise: BGL supercomputer and OpenStack cloud logs

**Scope.** For the BGL logs I looked at 4 Dec 2005 to 4 Jan 2006 (the end of the data) and compared it with the 31 days before. For the OpenStack logs I used everything there is, 14–17 May 2017; those logs start on 14 May, so nothing there can be called rising or new. All times are UTC, across all components and teams, looking only at the most severe levels. Every count below is exact.

## Ranked problems

**1. User programs fail to load when jobs start (BGL).** Jobs may not be starting at all.
- **Measured:** 13,952 fatal "permission denied" entries, up 91% on the previous month (7,296) [Q66]. Also 4,664 fatal "file not found" entries, up 64% (2,840), seen on 7 of 31 days [Q66][Q67]. A third kind, "not a valid program", has 1,024 entries on one day and did not appear the month before [Q66].
- **Spread:** 1,024 nodes each [Q68], all in the application component, owned by HPC Applications.
- **Why first:** fatal, rising, the most persistent of the rising problems, and the widest spread.
- **Possible explanation (hypothesis):** each failed launch may log one line per node. If so, these entries are a much smaller number of failed jobs. The cause could be wrong user paths or permissions rather than a system fault.
- **Next action:** HPC Applications to pull the most frequent failing program paths and owners, and decide whether this is user error or a permissions change on the system.

**2. Memory errors on two nodes (BGL).**
- **Measured:** 138 fatal entries, up 283% on the previous month (36), on 6 of 31 days [Q66][Q67]. The example entry is an uncorrectable memory error [Q64].
- **Spread:** only 7 nodes. Two of them produce most entries: 48 and 42 of the 138 [Q68]. Kernel component, owned by Node OS.
- **Why second:** fatal and rising sharply; it ranks below item 1 because it appeared on fewer days and on far fewer nodes.
- **Next action:** Node OS, with Hardware Reliability, to check the two nodes producing most of these and consider taking them out of service.

**3. File system mounts fail across almost the whole machine (BGL).**
- **Measured:** 2,202 fatal entries, up 825% on the previous month (238), on 4 of 31 days [Q66][Q67].
- **Spread:** 948 nodes [Q68]. Kernel component, owned by Node OS.
- **Why third:** fatal and the steepest rise, but it appeared on fewer days than items 1 and 2.
- **Possible explanation (hypothesis):** because nearly every node is affected, the cause may be on the shared file system side rather than in the nodes.
- **Next action:** Node OS to compare the 4 affected days with the file system's own records.

**4. One day of login and connection failures, not seen the month before (BGL).**
- **Measured:** 816 fatal "input/output error" entries when changing to the job's working directory, on 816 nodes. On the same day there were also 208 fatal "connection dropped after login" entries, on 208 nodes [Q66][Q68]. Neither appeared in the previous month [Q66].
- **Spread:** application component, owned by HPC Applications.
- **Why fourth:** fatal and new, but it happened on only one day. It may be a single incident.
- **Next action:** HPC Applications to review that day and confirm whether storage was unavailable then.

**5. Logins to the cloud failed at the same hour two days running (OpenStack).**
- **Measured:** 2 critical "unable to validate login token" entries, one each on 16 and 17 May, both in the 06:00 UTC hour [Q70]. Each came with an error saying the identity server was unavailable (code 503) [Q65][Q70].
- **Spread:** the token-check component of the cloud API service, owned by Identity & Access.
- **Why fifth:** this is the highest severity in the OpenStack logs, but there are very few entries and no trend can be measured.
- **Possible explanation (hypothesis):** something scheduled for 06:00 UTC daily may be taking the identity server down.
- **Next action:** Identity & Access to check what runs on the identity server around 06:00 UTC.
