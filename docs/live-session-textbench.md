## How to read this

- **Shortened results:** each tool result is cut to its first 12 lines and its `Evidence [Qn]` line. The full
  results and every query are in the raw sessions.
- **No editing:** answers are copied from the session without edits.
- **One follow-up:** the team-lead session ended by asking whether to run the 27.1 GB count. It got one reply in
  the same session (`--resume`): "Yes, go ahead with option 1." That is the only human input in the three sessions.
- **Not shown:** Claude Code's own `ToolSearch` calls, which load the tool schemas, are left out.
- **Not checked:** the answers were read but not checked against an independent count. Small differences between
  sessions are left as they are, e.g. Storefront by team (1,063,484,068) against service frontend (1,063,483,297).

## Possible cause (hypothesis)

The payment service seems to keep a per-card-type cache (here "Visa") that has a maximum size. Once it is full, every new Visa charge is rejected.

Why I think so:
- the message literally says the cache is full and "cannot add new item";
- the failure happens right after "Charge request received", with no other error before it;
- the rate is flat at about 1.8–2.0M entries per minute [Q9]. That fits a stuck "full" state better than an intermittent fault.

This dataset resembles the OpenTelemetry demo, which has a feature flag that simulates exactly this payment cache leak. That would make it a deliberately injected fault. This is unconfirmed.
